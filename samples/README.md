# 공개 캡처로 반증 조건 시험하기

설계 §10 의 반증 조건들은 **실제로 돌려봐야** 시험된다. 여기에 돌린 결과를 적는다.

## 하는 법

```bash
bash scripts/fetch-samples.sh          # 또는  pwsh scripts/fetch-samples.ps1
mvn -DskipTests package
java -Dstdout.encoding=UTF-8 -jar cli/target/huginn.jar \
    samples/4SICS-GeekLounge-151022.pcap samples/4SICS-GeekLounge-151022-policy.yaml
```

`editcap`(Wireshark)이 필요하다 — 배포본이 pcapng 이면 `PcapReader` 가 거부하므로 스크립트가
pcap 으로 정규화한다(2026-09-05 현재 세 파일 모두 이미 pcap 이라 변환은 일어나지 않는다).
캡처 자체는 커밋하지 않는다. 해시는 `SHA256SUMS` 에 기록돼 있다.

캡처 출처: **4SICS ICS Lab**, Netresec 배포 — 재배포·교육 사용 시 **CS3Sthlm** 을 명시해 달라는
것이 배포처의 요청이다. <https://www.netresec.com/?page=PCAP4SICS>

## 결과 (2026-09-05 · Modbus + S7comm · 갭 이후 구간 읽기)

| 캡처 | 처리 패킷 | 대상 외 패킷 | 해독한 대화 | 대상 외 대화 | UNDEC 대화 | UNDEC 관찰 | **미관측 바이트** | 위반 | 종료 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 151020 | 246,137 | 37,197 | 2 | 7,288 | 0 | 1 | **85,525 (2.4%)** | **23** | 1 |
| 151021 | 1,253,100 | 132,406 | 28 | 112,730 | 0 | 18 | **35,556 (0.3%)** | **73** | 1 |
| 151022 | 2,274,747 | 108,339 | 64 | 932,647 | 24 | 32 | **3,714 (0.0%)** | **21,070** | 1 |

정책은 세 캡처 모두 **관찰된 통신 중 일부만** 선언한다 — S7 폴러(`10.10.10.20`)의 **읽기만**
선언하고 쓰기와 나머지 호스트는 선언하지 않는다. 전부 선언하면 위반이 0건이라 대사가 실제로
도는지 알 수 없다. 151022 는 1차의 Modbus 규칙(폴러 → PLC 세 대 읽기)을 그대로 두고 S7 규칙만 더했다.

위반 내역:

| 캡처 | 내역 |
|---|---|
| 151020 | **HIGH 23** — 전부 `10.10.10.30` 이 PLC 에 보낸 S7 **쓰기**. 선언되지 않은 호스트가 PLC 에 쓰고 있다(갭 이후를 읽기 전에는 18 만 보였다) |
| 151021 | S7 HIGH 48 · S7 MEDIUM 14 + **Modbus MEDIUM 11 — `192.168.2.42` 가 PLC 여섯 대를 차례로 두드린 장비 열거 스캔**(`device-id:1`). 1차 §10 이 "Finding 이 되지 않는다" 고 적었던 바로 그것이다 |
| 151022 | Modbus HIGH 20,980 · **MEDIUM 69**(FC 43 해석으로 48 에서 +21) + S7 HIGH 14 · MEDIUM 7 |

## 판정

### ① `UNDECIDABLE` 비율 — 반증되지 않았다

151022 에서 관찰 49,767 건 중 `UNDECIDABLE` 은 48 건(0.1%)이다. S7 을 켠 뒤에도 판정 불가
대화는 늘지 않았다(151020·151021 은 0, 151022 는 1차와 같은 24).

### ② 프로토콜 선택 — 1차의 한계가 해소됐다

1차는 *"4SICS 는 S7comm 중심이고 Modbus 가 실린 캡처가 사실상 하나뿐이라 일반화할 수 없다"* 로
끝났다. **S7 을 붙이자 세 캡처 모두가 산업 통신을 내놓는다** — 151020 은 1차에서 Modbus 가 한
프레임도 없어 "위반 0 · 종료 0" 이던 캡처인데, 이제 미등록 호스트의 PLC 쓰기 18 건을 낸다.
프로토콜 선택이 틀린 게 아니라 **하나로는 부족했던 것**이라는 1차의 진단이 맞았다.

### ③ 이음매 — 통과

2차에서 `decode` 밖의 프로덕션 소스는 **두 곳, 네 줄**만 바뀌었다:

```
cli/src/main/java/dev/krillin/huginn/cli/Pipeline.java             | 6 +++---
reconcile/src/main/java/dev/krillin/huginn/reconcile/Protocol.java | 2 +-
```

`Protocol` 열거형 상수 하나와 `Pipeline` 의 진입점 이름(import·javadoc·호출)이 전부다.
1차 설계 §10 의 *"S7comm 을 붙일 때 `decode` 밖이 바뀌어야 하면 이음매를 잘못 잡은 것"* 은
**반증되지 않았다.** `ObservationResult`·`Report`·`contract`·`pcap` 은 한 줄도 바뀌지 않았고
`ModbusObserverTest` 20 건과 `cli` 테스트 11 건은 한 글자도 고치지 않은 채 통과한다.

### ④ 진짜 한계는 재조립 정책이었다 — 발견하고, 고쳤다

**발견.** tshark 가 세는 S7 요청(ROSCTR 1)은 23,732 / 86,403 / 53,217 인데 Huginn 은 처음에 **21 / 52,607 / 34,154** 만 관찰했다. 원인은 하나였다 — Huginn 이 재조립된 스트림의 `contiguousPrefix`, 즉 **첫 갭까지만** 읽었기 때문이다(1차 §5-③).

클라이언트 방향(`10.10.10.20:49156 → 10.10.10.10:102`) 실측:

| 캡처 | 세그먼트 | 전체 바이트 | 갭 | 첫 갭 위치 | 첫 갭까지 커버리지 | 당시 관찰 비율 |
|---|---:|---:|---:|---:|---:|---:|
| 151020 | 47,431 | 2,403,943 | 5 | 297 | 0.01% | 0.09% |
| 151021 | 172,651 | 8,547,957 | 1 | 5,200,371 | 60.84% | 60.88% |
| 151022 | 106,379 | 5,267,097 | 1 | 3,378,474 | 64.14% | 64.18% |

> **인용 정정.** 1차 §10 과 이 문서의 이전 판은 두 비율이 *"소수점 둘째 자리까지 일치"* 한다고 적었다. **틀렸다** — 151021·151022 는 둘째 자리에서 갈리고 **151020 은 0.01% 대 0.09% 로 9 배 차이**다(두 비율의 분모가 다르다: 앞은 한 스트림, 뒤는 캡처 전체의 ROSCTR 1). 정확한 진술은 *"같은 자릿수·같은 방향이며 한 스트림이 지배한다"* 이다.

**해소.** 갭 이후 구간을 **엄격 적합**(오프셋 0 에서 시작해 잔여 0 으로 끝날 때만 수용)으로 읽게 고쳤다. 경계를 찾아 스캔하지 않으므로 1차가 거부한 재동기화가 아니다.

| 캡처 | 이전 | 이후 | tshark ROSCTR 1 |
|---|---:|---:|---:|
| 151020 | 21 | **23,732** | 23,732 |
| 151021 | 52,607 | **86,403** | 86,403 |
| 151022 | 34,154 | **53,217** | 53,217 |

**근사가 아니라 완전 일치다.** 남을 수 있었던 두 원인(양방향 요청 대화·거부된 구간)이 이 데이터셋에서는 0 이다.

이 정책이 정당한 근거는 실측이다 — **프레임이 나오면서도 잔여가 남는 구간(지저분한 구간)이 세 캡처에서 하나도 없었다.** 갭이 패킷 단위로 생기고 한 패킷이 온전한 프레임을 나르므로 재개 지점이 프레임 경계에 떨어진다. 거부된 구간은 0 / 1 / 0 뿐이고, **대상 외 대화 수는 한 건도 줄지 않았다**(7,288 / 112,730 / 932,647) — 비산업 트래픽이 엄격 적합을 통과하지 않았다는 뜻이며, 그것이 오탐이 늘지 않았다는 증거다.

**그리고 리포트가 이제 못 본 것을 말한다.** 예전에는 "해독한 대화 2 · UNDECIDABLE 관찰 1" 로 보이면서 그 대화의 99.99% 를 못 봤다는 사실이 어디에도 없었다. 이제 `미관측 바이트 85,525 (2.4%)` 가 나온다 — 캡처에 없던 바이트(구멍)와 받았지만 해독 못 한 바이트를 합친 값이다. 받지 못한 것은 "미해독" 이 아니지만 **못 본 것은 맞다.**

### ⑤ 프로토콜별 커버리지 — 합산이 숨기던 것

2차 설계 §6 은 이음매 판정을 흐리지 않으려고 리포트를 합산으로 유지했고, 그 대가로 *"99% 가 S7 인 캡처에서 Modbus 가 얼마나 얇은지 알 수 없다"* 고 적었다. 판정이 끝난 뒤 표를 붙였다:

```
  프로토콜        해독 대화  UNDEC 대화        관찰  UNDEC 관찰       미관측 바이트
  MODBUS_TCP             0           0           0           0           0 (0.0%)   ← 151020
  S7COMM                 2           0      23,733           1      85,525 (2.4%)

  MODBUS_TCP            56          24      49,767          24       1,628 (0.0%)   ← 151022
  S7COMM                 8           0      53,218           8       2,086 (0.0%)
```

151020 의 `MODBUS_TCP 0` 행이 요점이다 — 1차가 산문으로만 적은 *"이 캡처에는 Modbus 가 한 프레임도 없다"* 를 **리포트가 직접 말한다.** 151022 는 Modbus 가 대화 수로는 7 배지만 관찰 수로는 S7 이 더 많다는 것이 한눈에 보인다. **판정은 바뀌지 않았다** — 위반도 종료 코드도 그대로다.

## 독립 검증 (tshark 4.6.8)

Huginn 은 포트를 보지 않고 프레이밍으로 판정하고 tshark 는 포트 기준으로 해석하므로, 둘이 맞으면
서로가 서로의 반증 시도가 된다.

| 대조 | tshark | Huginn | |
|---|---:|---:|---|
| 151020 총 프레임 | 246,137 | 246,137 (처리 패킷) | 일치 |
| 151020 비TCP·비IPv4 (ARP 4,389 + loop 2,481 + UDP 27,587 + ICMP 2,740) | 37,197 | 37,197 (대상 외 패킷) | 일치 |
| 151022 Modbus 요청 패킷 | 49,767 | 49,767 | 일치 |
| S7 을 나르는 TCP 스트림 수 (151020 / 151022) | 2 / 8 | 2 / 8 (해독 대화) | 일치 |
| S7 요청(ROSCTR 1) | 23,732 / 86,403 / 53,217 | 21 / 52,607 / 34,154 | **위 §④ 로 전량 설명** |
| S7 응답(ROSCTR 2·3) | 23,732 / 86,402 / 53,217 | **0 관찰** | 설계 §5-⑤ 준수 |
| 1200SYM 주소 (151020, `10.10.10.30` 요청) | area1 `0x0000` · area2 `0x0052` · LID 16×9·17×1·18×8 | `sym:m/16`×9 · `sym:m/17`×1 · `sym:m/18`×8 | **필드 단위 일치** |
| 한 대화를 두 해독기가 주장한 횟수 | — | **0** (세 캡처 모두) | 설계 §3 의 전제 성립 |

Modbus 응답 49,787 건과 S7 응답 76,951 건을 Huginn 은 **하나도 관찰하지 않았다** — 설계 §5-⑤
("요청만 `Observation` 이 된다")가 두 프로토콜 모두에서 실트래픽으로 확인됐다.

## 아직 검증되지 않은 것

- **S7ANY 주소 경로** — 실캡처의 주소는 100% 가 1200SYM 이고 S7ANY 는 0 건이다. 합성으로만 검증
- **1200SYM 의 `area1 != 0x0000` 경로** — 실캡처에 0 건. 그 경우 이름을 지어내지 않고 원시 표기로 낸다
- **CONTROL 계열**(PLC Start/Stop · 블록 다운로드) — 구현했지만 **합성 캡처로만 검증**했다. 4SICS 세 캡처에 이 여덟 함수코드가 0 건이라 실캡처 검증은 여전히 없고, 서브서비스를 읽지 않아 **과대분류인 면이 있다**
- **비표준 포트의 산업 통신** — Modbus 는 전부 502, S7 은 전부 102 였다. 우회 탐지는 합성 캡처로만 증명돼 있다
- **Modbus FC 43 의 MEI 13(CANopen)** — MEI 14 는 READ 로 판정하지만 MEI 13 은 읽기·쓰기를 모두 날라 `UNDECIDABLE` 로 남긴다. 세 캡처에 MEI 13 이 **0 건**이라 그 경로는 검증되지 않았다
