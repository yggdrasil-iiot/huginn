## 1. 왜 만드는가

2차 A단계의 실캡처 검증에서 나온 발견이 출발점이다. **진짜 한계는 프로토콜이 아니라 TCP 재조립 정책이었다.**

tshark 가 세는 S7 요청은 23,732 / 86,403 / 53,217 인데 Huginn 은 21 / 52,607 / 34,154 만 관찰했다. 원인은 하나다 — Huginn 은 재조립된 스트림의 **첫 갭까지만** 읽는다(1차 §5-③).

151020 은 오프셋 297 에서 51,183 바이트가 통째로 비어 있고, 그 뒤 2.4MB 를 못 본다. **그리고 리포트가 이 사실을 말하지 않는다** — "해독한 대화 2 · UNDECIDABLE 관찰 1" 로 보이지만 실제로는 그 대화의 대부분을 못 봤다.

### 실측이 방향을 정했다

갭 이후 구간을 잘라 실제 프레이머를 돌려본 결과(프로토타입, 저장소 변경 없음):

| 캡처 | 첫 구간 프레임 | 갭 이후 구간 프레임 | 깨끗한 구간 | **지저분한 구간** |
|---|---:|---:|---:|---:|
| 151020 | 24 | **47,422** | 10 / 10 | **0** |
| 151021 | 105,218 | **67,591** | 2 | **0** |
| 151022 | 68,308 | **38,126** | 2 | **0** |

> **단위 주의.** 이 표는 **양쪽 방향·모든 ROSCTR** 의 프레임을 센다(151021 의 105,218+67,591 ≈ tshark 의 요청 86,403 + 응답 86,402). Huginn 의 *관찰* 은 클라이언트 방향의 ROSCTR 1 뿐이므로, 151020 에서 기대되는 관찰 증가는 47,422 가 아니라 **약 23,700** 이다. 이 단위를 혼동하면 정상 구현을 2배 미달로 오해한다.

두 가지가 드러난다. 버리고 있던 양이 보고 있던 양보다 많고, **프레임이 나온 갭 이후 구간은 전부 잔여 0 으로 끝까지 깨끗하게 파싱된다.** 갭이 패킷 단위로 생기고 한 패킷이 온전한 프레임을 나르므로, 손실 이후 재개 지점이 프레임 경계에 떨어지기 때문이다.

### 갭이 있어도 미해독이 0 인 스트림이 실제로 있다

| 캡처 | 갭 있는 스트림 | 그중 **모든 구간 수용 + 미해독 0** |
|---|---:|---:|
| 151020 | 2 | **2** |
| 151021 | 9,407 | 2 |
| 151022 | 74 | 2 |

151020 의 S7 스트림 둘 — 47,000 프레임을 나르는 바로 그 스트림들 — 이 여기 해당한다. **이것이 §4 의 계수 정의를 강제한다**: "받았지만 해독 못 한 바이트" 만 세면 이 스트림들은 `0 (0%)` 로 나오고, 51,183 바이트 구멍 안의 프레임들은 어디에도 드러나지 않는다. 고치려던 거짓말을 형태만 바꿔 되풀이하는 셈이다.

### 인용 정정

1차 §10 과 `samples/README.md` §④ 는 관찰 비율과 커버리지가 *"소수점 둘째 자리까지 일치"* 한다고 적었다. **틀렸다.** 151021 은 60.84% 대 60.88%, 151022 는 64.14% 대 64.18% 로 가깝지만 둘째 자리에서 갈리고, **151020 은 0.01% 대 0.09% 로 9 배 차이**다(두 비율의 분모가 다르다 — 앞은 한 스트림, 뒤는 캡처 전체의 ROSCTR 1). 정확한 진술은 *"같은 자릿수·같은 방향이며 한 스트림이 지배한다"* 이고, 이 작업에서 **두 문서를 함께 고친다**(§6 파급 범위).

## 2. 범위

### 만든다

- `TcpStream` 이 **구간 목록**과 **갭 크기 합**을 낸다
- **엄격 적합** 규칙으로 갭 이후 구간을 해독한다 — 오프셋 0 에서 시작해 잔여 0 으로 끝날 때만 받는다
- 리포트에 **미관측 바이트와 비율**을 낸다

### 만들지 않는다 — 그리고 그 이유

| 제외 | 이유 |
|---|---|
| **재동기화**(경계를 찾아 앞으로 스캔) | 1차가 거부한 그것이다. 엄격 적합은 스캔하지 않는다 — 각 구간의 오프셋 0 하나만 시도한다 |
| **구간 안에서의 부분 수용** | 갭 이후 구간이 절반만 파싱되면 통째로 버린다. 중간부터 시작한 구간이 우연히 몇 프레임을 내는 경우를 걸러내는 것이 이 규칙의 목적이다 |
| **첫 구간 규칙 변경** | 지금도 첫 구간은 잔여를 허용하며 부분 파싱한다. 바꾸면 갭 없는 스트림까지 흔들려 회귀 표면이 불필요하게 넓어진다 |
| **대화별 손실 내역 리포트** | 93만 대화 캡처에서 리포트가 터진다. 총량과 비율만 낸다 |
| **COTP 분할 재조립** | 여전히 하지 않는다. 이 작업은 TCP 층의 갭을 다루는 것이지 응용 층 분할이 아니다 |
| **1차 §5-③ 의 폐기** | 갭 지점 이후를 *이어붙이지* 않는다는 원칙은 그대로다. 바뀌는 것은 "이어붙이지 않으므로 **버린다**" 에서 "이어붙이지 않고 **따로 읽는다**" 로다. §5-③ 의 문구는 이 작업에서 갱신한다 |

## 3. 구조

### `TcpStream` 이 구간 목록과 갭 크기를 낸다

```java
public record TcpStream(
    Instant at, String sourceAddress, int sourcePort, String targetAddress, int targetPort,
    List<byte[]> runs, long missingBytes, boolean truncated, boolean sawSynOnly) {

    /** 구간이 둘 이상이면 그 사이에 구멍이 있었다는 뜻이다. */
    public boolean hasGap() {
        return runs.size() > 1;
    }
}
```

`byte[] contiguousPrefix` 와 `boolean hasGap` 이 `List<byte[]> runs` 로 합쳐지고, **`missingBytes` 가 새로 생긴다** — 구간 사이 구멍들의 크기 합이다. 조립기는 이미 그 값을 안다(`compute()` 가 `sawGap` 을 세울 때 쓰는 `segStart - nextSeq`). 지금은 버리고 있을 뿐이다.

**`runs` 의 불변식:** 원소는 절대 빈 배열이 아니다. 데이터가 없는 스트림(SYN 만 잡힌 경우)은 `runs` 가 **빈 목록**이고 `missingBytes` 는 0 이다. `hasGap()` 은 그때 false 다.
`equals` 는 `byte[]` 때문에 여전히 참조 비교다 — 1차가 이미 한 번 데인 자리이므로 record 에 javadoc 으로 남긴다.

조립기는 지금처럼 seq 로 정렬하고 first-wins 로 겹침을 해소하되, 구멍을 만나면 구간을 끊고 크기를 누적한다.

### 프레이머는 손대지 않는다

`ModbusFramer`·`S7Framer` 는 "바이트 배열 하나를 자른다"는 순수 함수로 남는다. 테스트 21건도 그대로다. **프레이밍과 수용 정책을 섞지 않는 것**이 이 설계의 요점이다.

두 프레이밍 결과에 공통 인터페이스만 붙인다:

```java
/** 수용 정책이 프로토콜을 몰라도 되게 하는 최소 계약. */
interface Framing {
    int frameCount();
    int leftoverBytes();
}
```

`FramingResult` 는 `frames().size()`·`undecodedBytes()` 로, `S7FramingResult` 도 같은 방식으로 구현한다.

### 수용 정책과 스트림 읽기는 한 곳에 있다 — 호출부는 여섯이다

`contiguousPrefix()` 를 읽는 곳은 지금 **여섯 군데**다: `ModbusDecoder` 의 `scan`·관찰 루프·`shapeSignal`, `S7Decoder` 의 `scan`·Job 루프·관찰 루프. **여섯이 규칙을 각자 적용하면 방향 판정이 증거와 어긋난다** — `scan` 이 거부한 구간의 프레임을 `shapeSignal` 이 보면 Modbus R1(양쪽이 같은 형태)이나 S7 의 "요청 방향이 둘" 판정이 뒤집힐 수 있다. 프로토콜 사이의 발산보다 **한 프로토콜 안 호출부 사이의 발산**이 실제 위험이다.

그래서 스트림 하나를 읽는 일을 통째로 한 곳에 둔다:

```java
final class RunReader {

    /**
     * 스트림의 구간들을 프레이밍하고 <b>수용된 것만</b> 낸다.
     *
     * <p>수용 규칙 — <b>이 한 줄이 1차 원칙과의 경계선이다.</b> 첫 구간은 조건 없이 받고,
     * 이후 구간은 프레임이 하나 이상이고 잔여가 0 일 때만 받는다. 경계를 <b>찾지</b> 않으므로
     * 재동기화가 아니다. 중간부터 시작한 구간은 거의 확실히 걸러진다.
     */
    static <F extends Framing> Reading<F> read(TcpStream stream, Function<byte[], F> framer);

    /**
     * @param accepted     수용된 구간의 프레이밍 결과(구간 순서)
     * @param unreadBytes  받았지만 프레임이 덮지 못한 바이트 — 아래 표
     * @param capturedBytes 이 스트림에서 실제로 받은 바이트(모든 구간의 합)
     * @param rejectedRuns 거부한 구간 수 · @param dirtyRuns 그중 프레임이 나왔던 구간 수(§7 반증 조건)
     */
    record Reading<F>(List<F> accepted, long unreadBytes, long capturedBytes,
                      int rejectedRuns, int dirtyRuns) { }
}
```

여섯 호출부가 전부 이것을 부른다. 재프레이밍 비용도 줄어든다.

**`unreadBytes` 는 구간마다 이렇게 센다** — 2차가 세운 원칙("비-S7 TPKT 는 미해독 바이트가 아니다")을 깨지 않으려면 구간 길이를 통째로 세면 안 된다:

| 구간 | 계산 | 이유 |
|---|---|---|
| 첫 구간(항상 수용) | `leftoverBytes()` | 지금 동작 그대로 |
| 수용된 이후 구간 | 0 | 잔여 0 이 수용 조건이다 |
| 거부 · 프레임 0 | `leftoverBytes()` | COTP 연결 요청만 든 구간은 잔여 0 이라 **0 이 된다.** 2차 §219 가 "세면 CR/CC 만 오간 대화에 근거 없는 꼬리 UNDECIDABLE 이 붙는다"고 못박은 그 경우다 |
| 거부 · 프레임 있음(지저분한 구간) | **구간 전체 길이** | 읽을 수 있었으나 믿지 못해 통째로 버린 것이다. 잔여만 세면 버린 양을 축소 보고한다 |

### 꼬리 UNDECIDABLE 방아쇠는 그대로 넷이다

```java
if (client.unreadBytes() > 0 || client.stream().hasGap()
    || client.stream().truncated() || result.tailUndecidable()) {
```

**`hasGap()` 을 반드시 남긴다.** §1 의 두 번째 표가 이유다 — 151020 의 S7 스트림 둘은 갭이 있는데도 모든 구간이 수용되어 `unreadBytes == 0` 이다. `hasGap()` 을 빼면 그 대화들이 "완전히 해독했다"로 보고되고, 51,183 바이트 구멍 안의 프레임은 어디에도 드러나지 않는다.

**구간을 버렸으면 그 대화는 여전히 꼬리 UNDECIDABLE 을 단다.** 커버리지가 늘어도 "다 봤다"고 말하지 않는다.

## 4. 계수와 리포트

**대화 계수 셋은 그대로다.** 정의도, 합이 전체 대화 수라는 불변식도 건드리지 않는다.

`ObservationResult` 가 필드 둘을 얻는다:

```java
public record ObservationResult(List<Observation> observations,
                                int decodedConversations, int undecidableConversations,
                                int skippedConversations,
                                long unobservedBytes, long industrialBytes) { }
```

**정의 — 분자와 분모는 같은 집합 위에서 센다.** 대상 외가 아닌 대화(해독기가 주장한 대화)의 **모든 스트림**에 대해:

- `industrialBytes` = Σ (`capturedBytes` + `missingBytes`) — 그 대화가 실제로 오갔던 바이트
- `unobservedBytes` = Σ (`unreadBytes` + `missingBytes`) — 그중 우리가 보지 못한 바이트

**캡처에 없던 바이트를 분자·분모 양쪽에 넣는 것이 이 정의의 핵심이다.** 받지 못한 것은 "미해독" 이 아니지만 **못 본 것은 맞다.** 운영자의 질문은 "이 대화를 얼마나 못 봤나" 이고, 그 답은 둘의 합이다.

대상 외 대화는 양쪽 어디에도 넣지 않는다 — 애초에 읽기로 한 트래픽이 아니라서, 넣으면 지표가 SSH·DNS 양에 지배된다(1차가 `UNDECIDABLE` 대화에서 겪은 함정이다). 순회기가 대상 외 대화를 만나면 누적 전에 빠져나가므로 이 배제는 규칙이 아니라 구조로 지켜진다.

리포트는 한 줄이 늘어 **일곱 줄**이 된다:

```
  미관측 바이트      1,234,567 (36.2%)
```

비율은 **소수 한 자리**로 낸다 — 정수로 자르면 0.4% 가 `0%` 가 되어 실제 손실을 숨긴다. 분모가 0 이면 `0 (0.0%)` 로 적는다. `Report` 의 `count(String, int)` 는 `long` 을 받지 못하므로 확장하고, 표시 폭 padding 규칙은 새 라벨에도 그대로 적용한다.

**이 수치와 `UNDECIDABLE` 대화 수는 서로 다른 실패를 센다.** 앞은 *보지 못한 것*이고 뒤는 *보았으나 판정하지 못한 것*이다. 두 줄이 각자 다른 질문에 답한다.

**종료 코드 계약은 그대로다.** 미관측이 아무리 많아도 위반이 0 이면 0 이다.

**진단(`Diagnosed`)에 둘을 더한다** — `rejectedRuns` 와 `dirtyRuns`. §7 의 반증 조건이 이 수치 없이는 측정 불가다. 리포트에는 내지 않는다(§2 의 합산 유지).

## 5. 회귀 표면 — 어디까지 움직이는가

**스트림 단위로는 갭 없는 스트림이 비트 단위로 동일하다.** `runs == [prefix]` 이면 첫 구간은 무조건 수용되고, 프레이머가 같은 배열을 보고, `unreadBytes` 가 옛 `leftoverBytes` 와 같고, 관찰 순서도 같다.

**그러나 판정 단위는 대화다.** 다음 셋은 갭 없는 스트림만 보고 판단하면 놓친다:

1. 갭 없는 클라이언트 스트림 + 갭 있는 서버 스트림인 대화는 움직인다(방향 판정 입력이 바뀐다)
2. **대상 외였던 대화가 산업 대화로 넘어올 수 있다** — 비산업 트래픽의 갭 이후 구간이 우연히 엄격 적합을 통과하면 세 계수가 전부 움직인다. §7 의 반증 조건이 이것을 겨냥한다
3. 갭 때문에 판정 불가였던 대화가 해독으로 넘어갈 수 있다

정확한 진술은 *"회귀 표면은 **갭 있는 스트림을 포함한 대화**"* 다.

## 7. 이 설계가 틀렸다고 판명되는 조건

- **실캡처에서 지저분한 구간(`dirtyRuns > 0`)이 발견되면** → 엄격 적합이 경계 정렬을 보장한다는 전제가 틀린 것이다. 지금은 세 캡처에서 0 이며, **0 이라는 사실을 회귀로 지켜야** 이 정책이 계속 정당하다. `Diagnosed.dirtyRuns` 로 측정한다
- **대상 외 대화 수가 크게 줄면**(`932,647 / 112,730 / 7,288` 기준) → 비산업 트래픽의 갭 이후 구간이 엄격 적합을 통과하고 있다는 뜻이고, 그것이 곧 오탐이다. 1차의 "오탐이 오검출보다 비싸다"가 여전히 우선한다
- **갭 없는 스트림만으로 이뤄진 대화의 판정이 하나라도 움직이면** → 첫 구간 처리를 건드리지 않겠다는 약속이 깨진 것이다
- **미관측 바이트가 0 인데 관찰 수가 tshark 와 크게 다르면** → 손실의 원인이 재조립이 아닌 다른 곳에 있다는 뜻이고, 이 작업이 겨냥한 문제가 아니었던 것이다
- **엄격 적합으로 받은 구간의 관찰이 실제로는 오탐이면** → 규칙이 느슨한 것이다. 대상 외 대화 수와 함께 본다
