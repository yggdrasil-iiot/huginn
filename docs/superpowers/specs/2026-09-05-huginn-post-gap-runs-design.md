# Huginn — 갭 이후 구간 처리

- 상태: 초안 (2026-09-05)
- 선행: [1차 설계](2026-09-05-huginn-design.md) · [2차 S7comm 설계](2026-09-05-huginn-s7comm-design.md)
- 저장소 `yggdrasil-iiot/huginn` · Java 17 · Apache-2.0

---

## 1. 왜 만드는가

2차 A단계의 실캡처 검증에서 나온 발견이 출발점이다. **진짜 한계는 프로토콜이 아니라 TCP 재조립 정책이었다.**

tshark 가 세는 S7 요청은 23,732 / 86,403 / 53,217 인데 Huginn 은 21 / 52,607 / 34,154 만 관찰했다. 차이는 전부 한 가지로 설명된다 — Huginn 은 재조립된 스트림의 **첫 갭까지만** 읽는다(1차 §5-③). 클라이언트 방향의 첫 갭까지 커버리지(0.01% / 60.84% / 64.14%)가 관찰 비율(0.09% / 60.88% / 64.18%)과 소수점 둘째 자리까지 일치한다.

151020 은 오프셋 297 에서 51,183 바이트가 통째로 비어 있고, 그 뒤 2.4MB·약 23,700 요청을 못 본다. **그리고 리포트가 이 사실을 말하지 않는다** — "해독한 대화 2 · UNDECIDABLE 관찰 1" 로 보이지만 실제로는 그 대화의 99.99% 를 못 봤다.

### 실측이 방향을 정했다

갭 이후 구간을 잘라 실제 프레이머를 돌려본 결과(프로토타입, 저장소 변경 없음):

| 캡처 | 첫 구간 프레임 | 갭 이후 구간 프레임 | 깨끗한 구간 | **지저분한 구간** |
|---|---:|---:|---:|---:|
| 151020 | 24 | **47,422** | 10 / 10 | **0** |
| 151021 | 105,218 | **67,591** | 2 | **0** |
| 151022 | 68,308 | **38,126** | 2 | **0** |

두 가지가 드러난다. 버리고 있던 양이 보고 있던 양보다 많고, **프레임이 나온 갭 이후 구간은 전부 잔여 0 으로 끝까지 깨끗하게 파싱된다.** 갭이 패킷 단위로 생기고 한 패킷이 온전한 프레임을 나르므로, 손실 이후 재개 지점이 프레임 경계에 떨어지기 때문이다.

## 2. 범위

### 만든다

- `TcpStream` 이 **구간 목록**을 낸다(첫 갭까지가 아니라)
- **엄격 적합** 규칙으로 갭 이후 구간을 해독한다 — 오프셋 0 에서 시작해 잔여 0 으로 끝날 때만 받는다
- 리포트에 **미해독 바이트와 비율**을 낸다

### 만들지 않는다 — 그리고 그 이유

| 제외 | 이유 |
|---|---|
| **재동기화**(경계를 찾아 앞으로 스캔) | 1차가 거부한 그것이다. 엄격 적합은 스캔하지 않는다 — 각 구간의 오프셋 0 하나만 시도한다 |
| **구간 안에서의 부분 수용** | 갭 이후 구간이 절반만 파싱되면 통째로 버린다. 중간부터 시작한 구간이 우연히 몇 프레임을 내는 경우를 걸러내는 것이 이 규칙의 목적이다 |
| **첫 구간 규칙 변경** | 지금도 첫 구간은 잔여를 허용하며 부분 파싱한다. 바꾸면 갭 없는 스트림의 동작까지 흔들려 회귀 표면이 불필요하게 넓어진다 |
| **대화별 손실 내역 리포트** | 93만 대화 캡처에서 리포트가 터진다. 총량과 비율만 낸다 |
| **COTP 분할 재조립** | 여전히 하지 않는다. 이 작업은 TCP 층의 갭을 다루는 것이지 응용 층 분할이 아니다 |

## 3. 구조

### `TcpStream` 이 구간 목록을 낸다

```java
public record TcpStream(
    Instant at, String sourceAddress, int sourcePort, String targetAddress, int targetPort,
    List<byte[]> runs, boolean truncated, boolean sawSynOnly) {

    /** 구간이 둘 이상이면 그 사이에 구멍이 있었다는 뜻이다. */
    public boolean hasGap() {
        return runs.size() > 1;
    }
}
```

`byte[] contiguousPrefix` 와 `boolean hasGap` 두 컴포넌트가 `List<byte[]> runs` 하나로 합쳐진다. `hasGap()` 은 파생 메서드로 남아 호출부(순회기의 꼬리 UNDECIDABLE 규칙)가 그대로 돌아간다.

조립기는 지금처럼 seq 로 정렬하고 first-wins 로 겹침을 해소하되, **구멍을 만나면 구간을 끊고 새로 시작한다.** 데이터가 없으면 구간은 빈 목록이다.

### 프레이머는 손대지 않는다

`ModbusFramer`·`S7Framer` 는 "바이트 배열 하나를 자른다"는 순수 함수로 남는다. 테스트 21건도 그대로다. **프레이밍과 수용 정책을 섞지 않는 것**이 이 설계의 요점이다.

### 수용 정책은 한 파일에 있다

```java
/**
 * 갭 이후 구간을 받을지 정한다. <b>이 세 줄이 1차 원칙과의 경계선이다.</b>
 *
 * <p>경계를 <b>찾지</b> 않으므로 재동기화가 아니다 — 각 구간의 오프셋 0 하나만 시도하고,
 * 끝까지 정확히 떨어질 때만 받는다. 중간부터 시작한 구간은 거의 확실히 걸러진다.
 */
static boolean accept(int runIndex, int frameCount, int leftoverBytes) {
    return runIndex == 0 || (frameCount > 0 && leftoverBytes == 0);
}
```

`ModbusDecoder`·`S7Decoder` 가 `stream.runs()` 를 돌면서 이것을 부른다. 정책이 한 곳에 있어 두 프로토콜에서 갈라질 수 없다.

**첫 구간은 조건 없이 받는다.** 지금 동작 그대로이며, 그래서 **갭이 없는 스트림은 동작이 비트 단위로 동일하다.** 회귀 표면이 갭 있는 스트림으로 정확히 한정된다.

### `StreamEvidence` 가 바이트 수를 싣는다

```java
/**
 * @param unreadBytes 이 스트림에서 프레임이 덮지 못한 바이트 — 첫 구간의 잔여 + 거부된 구간 전체
 * @param totalBytes  이 스트림의 전체 바이트(모든 구간의 합)
 */
record StreamEvidence(TcpStream stream, int frameCount, long unreadBytes, long totalBytes) { }
```

`boolean leftoverBytes` 를 대신한다. 꼬리 UNDECIDABLE 판정은 `unreadBytes > 0` 으로 그대로 성립하고, 같은 값이 리포트의 분자가 된다.

**구간을 버렸으면 그 대화는 여전히 꼬리 UNDECIDABLE 을 단다.** 커버리지가 늘어도 "다 봤다"고 말하지 않는다.

## 4. 계수와 리포트

**대화 계수 셋은 그대로다.** 해독/대상 외/UNDECIDABLE 의 정의도, 합이 전체 대화 수라는 불변식도 건드리지 않는다.

`ObservationResult` 가 필드 둘을 얻는다:

```java
public record ObservationResult(List<Observation> observations,
                                int decodedConversations, int undecidableConversations,
                                int skippedConversations,
                                long unreadBytes, long industrialBytes) { }
```

리포트는 한 줄이 늘어 일곱 줄이 된다:

```
  미해독 바이트      1,234,567 (36%)
```

**분모는 산업 대화에 속한 스트림의 전체 바이트다.** 대상 외 대화는 분자에도 분모에도 넣지 않는다 — 애초에 읽기로 한 트래픽이 아니라서, 넣으면 지표가 SSH·DNS 양에 지배된다(1차가 `UNDECIDABLE` 대화에서 겪은 함정이다). 분모가 0 이면 비율을 내지 않고 `0 (0%)` 로 적는다.

**이 수치와 `UNDECIDABLE` 대화 수는 서로 다른 실패를 센다.** 앞은 *읽지 못한 것*이고 뒤는 *읽었으나 판정하지 못한 것*이다. 양쪽 방향에 요청이 있어 판정 불가가 된 대화는 프레임을 다 읽었으므로 미해독 바이트가 0 일 수 있다 — 그게 맞다. 두 줄이 각자 다른 질문에 답한다.

**종료 코드 계약은 그대로다.** 미해독이 아무리 많아도 위반이 0 이면 0 이다.

## 5. 검증

### 갭 없는 스트림은 동작이 같다

`pcap` 테스트 14건은 `contiguousPrefix()` → `runs().get(0)` 으로 **표현만** 바뀌고 단언 값은 그대로여야 한다. 값을 고쳐야 한다면 표현 변경이 아니라 동작 변경이므로 멈추고 원인을 찾는다.

`decode`·`cli` 의 기존 테스트도 갭 없는 픽스처를 쓰므로 그대로 통과해야 한다 — 단, `ObservationResult` 에 필드가 늘어 생성자를 부르는 테스트는 컴파일이 깨진다. 그 수정은 표현 변경이다.

### 실캡처 기대

- **S7 프레임 관찰이 크게 오른다.** 프로토타입 기준 151020 의 갭 이후 구간에만 47,422 프레임이 있다. 정확한 값은 구현 후 측정해 `samples/README.md` 에 기록한다
- **Modbus 수치는 움직일 수 있다.** 1차의 151022 기준선(위반 21,028 · 해독 56 · UNDECIDABLE 대화 24)은 갭 없는 스트림에서 나온 것이라 그대로일 가능성이 높지만, 갭 때문에 판정 불가였던 대화가 해독으로 넘어가면 바뀐다. **바뀌면 1차 판정을 고치는 게 아니라 정책이 바뀌었음을 적고 새 기준선을 잡는다** — 이번 수치 변화는 의도된 결과다

### 새 테스트

- 수용 정책 단위 — 첫 구간은 무조건, 이후 구간은 프레임 1개 이상 + 잔여 0 일 때만
- 갭 있는 스트림에서 갭 이후 구간이 실제로 해독된다
- 중간부터 시작한 구간(첫 프레임이 잘린 채 시작)은 거부된다
- 거부된 구간이 있으면 꼬리 `UNDECIDABLE` 이 그대로 붙는다
- 미해독 바이트가 정확히 세이고 리포트에 비율과 함께 나온다

## 6. 이 설계가 틀렸다고 판명되는 조건

- **실캡처에서 지저분한 구간(프레임이 나오면서도 잔여가 남는 갭 이후 구간)이 발견되면** → 엄격 적합이 경계 정렬을 보장한다는 전제가 틀린 것이다. 지금은 세 캡처에서 0 이며, **0 이라는 사실 자체를 회귀로 지켜야** 이 정책이 계속 정당하다
- **갭 없는 스트림의 판정이 하나라도 움직이면** → 첫 구간 처리를 건드리지 않겠다는 약속이 깨진 것이다
- **미해독 바이트가 0 인데 관찰 수가 tshark 와 크게 다르면** → 손실의 원인이 재조립이 아닌 다른 곳에 있다는 뜻이고, 이 작업이 겨냥한 문제가 아니었던 것이다
- **엄격 적합으로 받은 구간에서 나온 관찰이 실제로는 오탐이면**(예: 우연히 맞아떨어진 바이트열) → 규칙이 느슨한 것이다. 1차가 "오탐이 오검출보다 비싸다"고 한 판단이 여전히 우선한다
